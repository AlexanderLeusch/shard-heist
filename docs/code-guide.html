01 · Overview

The game at a glance

Shard Heist is a 3D police-chase game that runs entirely in the browser as a static website: one page, one stylesheet and three scripts. The player picks a map (Lisbon's Baixa, Highway or Countryside) and a getaway vehicle (Car, Motorcycle or Truck), collects glowing star shards, escapes up to four police cars and a helicopter, and reaches a finish gate before the clock runs out. Five wanted stars make the chase harder over time. All three maps have hills that slow the player down or speed them up. Crashes cause visible damage; repair kits remove it; police can bust the player when they box the vehicle in. Seven radio stations play while driving, all synthesised by the game. The story mode The Necklace Job is an option in the same main menu (section 10).

03 · Assessment

How complex is this code?

Overall: medium to high for a browser game without a framework. In size it sits between a weekend game jam entry (typically 500 to 1,500 lines) and a small indie prototype. What makes it demanding is not the line count but the number of independent systems that cooperate every frame: three procedurally generated worlds, three traffic AIs, a police AI with navigation, arcade physics with collision response, a synthesised engine sound and radio, and a post-processing render pipeline.

What helps readability

  • Clear section headers with ### explanations at the top of each of the 25 sections and above each important function.
  • The rules are pure functions in src/core.js with automated tests, separate from rendering and audio.
  • All tuning lives in a few tables (MODES, VEH and ENGINES in core.js, STORY in game.js); the menu stats are computed from them.
  • Each map is a “world” object with the same shape: group, colliders, radar shapes.

What makes it harder to maintain

  • game.js is one closure: its sections can read each other’s variables (for example car, mode, police).
  • The 3D, AI and audio code in game.js is only covered by the browser smoke test, not by unit tests.
  • Mode-specific branches (if (mode === 'country')) are spread across physics, police, HUD and pickups.
Effort estimate. A developer who knows three.js needs roughly one to two days to understand the whole code well enough to change it safely; with this guide, about half a day to find their way.
04 · Architecture

Architecture and frame loop

The site has five files that load in a fixed order: index.html (HUD, menus, error screen), styles.css, src/boot.js (error screen, loaded first), then three.js, src/core.js (the rules as pure functions) and src/game.js (one closure with the rest of the game). At start-up the script generates textures and the city, builds the vehicles and police, sets up the renderer, pre-compiles all shaders and shows the menu. The highway and countryside are built only when first selected.

The frame loop

frame(now) runs once per display refresh via requestAnimationFrame. The time step dt (Core.frameDt) is never negative and capped at 50 ms, so a slow frame never teleports a vehicle through a wall.

// simplified from the Loop section

else if (state !== 'pause') { /* menu orbits the showroom, results keep the world alive */ }

updateHeli; updateParticles; updateSmoke; updatePoliceVisuals; updateShowroom; updateBoundary; applyCarMesh
updateEngine; updateRadio; updateHud; drawRadar
composer.render()  or  renderer.render(scene, camera)               // Ultra vs Balanced

06 · Worlds and AI

Worlds, traffic and police AI

World objects

Every map is represented by the same structure: { group, colliders, radar }. group holds all meshes so a whole map can be shown or hidden at once. colliders lists boxes (t:'b' buildings, 'p' parked cars, 'w' walls) and circles ('c' trees, poles). radar holds rectangles drawn on the mini map. The countryside also keeps a 24 m spatial grid so collidersNear() only tests nearby trees out of ~3,000.

City

Lisbon's Baixa as a 6×6 grid of 48 m blocks with 14 m streets. A block is a closed row of Pombaline houses (block()): each floor picks its row in the facade texture (FRONT_ROWS), so the first floor has the tallest windows and the balconies; a mask (frontMat) tints only the plaster, not the limestone. Other blocks are a park or a square. The Arco da Rua Augusta, the National Theatre, Rossio station, the Praça do Comércio towers, the Sé, the river and the bridge are placed by hand. Core.streetAt names the street under the car. Lamp posts at block corners double as traffic-light poles. The hills around the valley paint their own colours and ignore the fog, or night would turn them the colour of the sky and the houses would seem to float.

Highway

A straight 4 km corridor: textured road, dashed lanes, a median barrier and guard rails as long wall colliders, median lights with light cones, sign gantries, forests, hills and a skyline at the finish.

Countryside

A Catmull-Rom spline through 15 seeded control points, sampled every ~2 m. The terrain height field (6 m cells) uses noise hills flattened within 9–75 m of the road, coloured as fields, verges and forest.

Seeded randomness

Layouts use mulberry32(seed), so every player sees the same city and road. Shard positions use Math.random() and change every run.

Hills

Core.hillHeight is one height field per map. Each world is built flat, then laySlopes() bends it over the field once. Big meshes are first baked into world space, because the ground planes are built lying on their side. Ground-level triangles are cut on the grid of Core.hillMesh, so road, kerb, markings and tracks stay exactly parallel and cannot pass through each other. Small objects and instances move as one, so lamps and trees stay upright. Vehicles use the same surface every frame: the player follows it exactly, and only a kerb's step is smoothed. Note that the real Baixa is flat: its hills are a game decision.

Road coordinates on the countryside

Traffic and police on the country road think in road coordinates: s (metres along the road) and lat (sideways offset, positive = right of travel). roadPoint(s, lat) converts to world x, z and heading, interpolating between samples so motion is smooth. roadQuery(x, z) does the reverse with a cached search window.

Three traffic systems

MapModelBehaviour
CityNode to node on a gridRight-hand lane to the next intersection, straight / left / right on a circular arc (3.5 m or 10.5 m radius), stops at red and amber, keeps distance, stops briefly when hit. Leftover distance carries over between straight and arc.
HighwayFixed lanes, position along zLane-dependent cruise speed (fast left lane, lorries right), car-following behind any vehicle including player and police, recycled 380–760 m ahead or behind.
CountrysidePosition s along the splineBoth directions in their own lane, same car-following rule, recycled around the player’s s.

All three use the same following rule: desired = min(cruise, speedAhead + (gap − safeGap) × k), approached smoothly (proportional change, at most 14 m/s² braking).

Police AI

  • Wanted stars: Core.wantedStars gives 1 to 5 stars from the time on the run or the progress, whichever is further along. Core.PURSUIT says what each star means: 1 to 4 cars, up to 10 % faster, quicker reinforcements, tougher cars.
  • Helicopter: joins after 60 seconds, or sooner with the fifth star, and hunts the player. Its searchlight tracks the player at 94 % of police speed (Core.trackStep); in the light the police are 6 % faster and see further. The beam is a cone and a ground glow, not a light source, so no shader has to recompile. The rotor sound is a tested loop (Core.rotorLoop): four blades at six turns a second make 24 thumps a second, over the tail rotor, turbine and air rumble; it gets louder and brighter as the helicopter nears, with a slight Doppler shift.
  • Navigation: city cars follow the street grid until segmentBlocked() reports a clear line of sight, then drive at the predicted player position. Highway cars stay on their side and swerve around traffic. Country cars follow the road 24 m ahead until within 40 m.
  • Speed control: slower in sharp turns, faster when far behind, off-road penalty in the countryside, reverse manoeuvre when stuck for 1.2 s.
  • Contact: the closing speed decides damage to the player (× vehicle dmg) and to the police car (× vehicle ram). A police car has 3 to 4 “hit points”, set by the stars.
  • Bust: a police car within 9 m while the player is below ~16 km/h fills the bust meter in 2.2 s; it drains when the player moves away.
  • Light bar: each car flashes red/blue sprites plus one real point light. The four point lights stay in the scene permanently (see section 08).
07 · Physics

Physics, boundary and camera

The driving model is arcade-style and deterministic per frame. It does not simulate tyres or mass; it combines a few simple rules that feel right at speed.

// acceleration under throttle (also used by the menu's 0–80 km/h figure)
a = 24 · VEH.accel · (1 − (speed / maxNow)^1.6 · 0.8)        // m/s²
maxNow = MODES.max · VEH.speed · (1 − 0.4 · damage/100) · (off-road ? 0.55 : 1) · (1 − clamp(grade · 2.6 / √VEH.accel, −0.22, 0.32))
// a slope also pulls directly: grade is the rise per metre along the direction of travel
a_slope = −42 · grade                                        // m/s²
// steering: yaw rate falls with speed
turn = steer · min(1, v/6) · 2.5 · VEH.handling / (1 + 0.035 · v)
// damage per crash
damage += max(0, (impact − 4) · 1.0 · VEH.dmg)              // impact = closing speed in m/s

Collisions

Each vehicle is approximated by 1–3 circles along its length (VEH.samples, radius VEH.r). collidePoint() tests a circle against a box or circle and returns the push-out normal and depth. Above 2 m/s into the obstacle it counts as a crash (speed drops to 30 %, damage and sparks); below it the vehicle slides along. Traffic and police use the same function with relative velocity.

Map boundary

Every map has an edge: the square around downtown (±150 m), the start and end walls of the highway, and the rim of the countryside terrain. boundaryDistance() returns how far the player is from it.

Distance to edgeFeedback

Ground, slopes and cameras

groundH(x, z) returns the hill height at a point, plus 0.18 m on city kerbs and the interpolated terrain in the countryside; the vehicle samples four points for pitch and roll. The chase camera follows with speed-dependent distance and field of view, shakes on crashes, is pulled out of buildings by a ray test (camClip) and kept above hills. In the menu the showroom camera orbits the vehicle and setViewOffset places it beside the menu panel.

08 · Rendering

Graphics pipeline and performance

StageTechnique
ColourAll hex colours are sRGB and converted to linear by a small patch on THREE.Color.setHex; output uses ACES filmic tone mapping.
Sky and reflectionsGLSL gradient shader on a sphere, rendered once into a PMREM environment map so glass and clear-coat paint reflect it.
Draw-call budgetBatching (one mesh per material for a whole map) and instancing (one draw per vehicle part for whole fleets, trees, parked cars).
MaterialsPBR: MeshStandardMaterial, MeshPhysicalMaterial with clear coat for paint, emissive maps for lit windows and signs.
SurfacesGenerated colour, roughness and normal maps: wet asphalt with low-roughness puddles, paving joints, grass.
ShadowsOne directional sun with PCF soft shadows; its 120 m shadow box follows the player in whole shadow pixels (Core.snapShadow), so shadow edges do not crawl over the walls. 4096² on Ultra, 2048² on Balanced, half of that on phones.
Fake volumetricsAdditive cones under lamps and in front of headlights; glow sprites and points for lamps and vehicle lights.
Post-processingUltra: multisampled render target with 24-bit depth → UnrealBloom → gamma correction (FXAA on WebGL1). Balanced: direct render. In both, Core.stepQuality lowers the resolution while the frame rate stays low.

Why there is no stutter when police arrive

three.js compiles a separate shader program for every combination of material and number of lights. The police cars originally carried their point light inside the car’s group; hiding or showing a car changed the light count, and every material in the scene was recompiled in the middle of a chase.

  • Police point lights live in the scene permanently and are only switched on and off.
  • warmUp() compiles every shader at start-up and at each run, temporarily making hidden objects (police cars, gate, smoke, courier) visible to the compiler.
  • Smaller savings: one obstacle list per frame instead of one per caller, a stamp-based collider lookup instead of a quadratic duplicate check, and spark materials are freed after use.

Vehicle bodies

A car starts as a 2D side silhouette with arcs for the wheel arches. extrudeProfile extrudes it with bevelled edges, shapeBody pulls vertices inwards towards the roof (tumblehome) and at the corners, and smoothGeo welds vertices so the paint shades smoothly. Glass, lights, lenses and chrome are separate parts with their own materials.

09 · Sound and interface

Sound, damage, HUD and menu

Engine sound

The engine is a small physical model in core.js. engineLoop() sends one pressure pulse per cylinder firing into an exhaust pipe that reflects at its open end, then through muffler resonances that stay at the same frequencies at every rpm. The firing frequency is rpm / 60 × cylinders / 2: a 6,000 rpm V8 fires at 400 Hz, a 1,500 rpm truck six at 75 Hz. engineLoops() renders each engine at five rpms, once under load and once on overrun, because a real engine sounds different when the driver lifts. The lowest rpm has an idle loop instead: slow, soft pulses through a closed-down muffler, cylinders firing unevenly so the V8 lopes once per cycle, with valve train or diesel knock on top. While running, its pitch slowly hunts by about 2 %. The engine sits below the music in the mix, and drops further while the radio plays. updateEngine() pitches the loops to the current rpm and crossfades by rpm and throttle, the way racing games blend recorded engine loops.

  • Signal chain: loops → compressor. All character is in the loops, so nothing has to be filtered at runtime.
  • Gearbox: Core.gearFor and Core.engineTarget, both tested. The throttle closes for each gear change and the revs fall to what the next gear asks for. A rev limiter cuts the fuel at the top.
  • Other layers: road rumble (stronger off-road), gearbox whine (strongest in reverse), wind rising with speed², tyre squeal, police siren with distance-based volume. A badly damaged engine misfires.
  • Radio: seven stations. Core.radioBar writes one bar as notes; radioNote plays each on a synthesised instrument, scheduled ahead on the audio clock. No music files. The tunes come from seeded random walks; the classical station plays Bach and Beethoven, both in the public domain.
  • Visible damage: Core.damageStage gives four stages. Each model lists its loose parts (damageParts), dentShader dents and scratches the paint with one uniform, and Core.smokeFor sets the smoke from thin grey to a black column, with flames at 88 %.
  • Skid marks: Core.skidAmount says how hard the rear tyres slide, for the marks, the tyre smoke and the squeal. updateSkids writes dark strips to a fixed ring of 900 quads, placed with groundH so they lie on the hills; the oldest fade before they are overwritten.
  • Silence rules: silent in the menu and pause; all audio is suspended while the tab is hidden.

10 · Story mode edition

The Necklace Job

A three-act campaign, started from the main menu, that continues Plot Twist – The Missing Necklace and starts where room 1 ends: inmate 4471 has escaped through the tunnel, and Officer Hale, a secret ally, helps over the radio (his lines are orange, police dispatch is red). The detective who investigated the stolen Starfall necklace is framed for the theft; the mastermind is the necklace’s owner, Lady Ashford, who staged it for the insurance money. Free ride stays available next to it.

How it is built

  • STORY holds the acts and a timeline of narrator and police-radio lines per act; updateStory() plays them as HUD messages and names the player’s vehicle in the radio calls.
  • startStoryAct(i) reuses startRun() for the act’s map, then adds the letter (placeEnvelope) or the courier lorry (setupCourier).
  • finish() and gameOver() hand over to storyFinish() and storyGameOver() when a story is running; showEnding() picks Ending A or B from story.letter.
  • The rules are in core.js and tested in tests/story.test.js: beginAct (only acts 1–3), retryAct, finishOpen (the toll needs the clasp), storyEnding (A or B) and dueRadio (each radio line once).
  • The courier lorry drives in the right lane with the same car-following rule as traffic, stops before the toll, and is collidable; traffic treats it as an obstacle.
Design rule carried over from the original project: the letter is optional but decides the ending. Players who only follow the obvious path reach Ending B; players who explore reach the truth.
11 · Tuning

12 · Outlook

Limitations and next steps

Known limitations

  • Look: procedural geometry and textures cannot reach photo-realism; vehicles and buildings are stylised. On hills the building fronts follow the slope instead of stepping.
  • Sound: the engines, rotor and radio are synthesised approximations, not recordings. They were checked by measurement (firing frequency, level, spectrum), so they should also be judged by ear.
  • Performance: Ultra (bloom, 4096² shadows, 2048² facades) needs a decent GPU; phones default to Balanced. The hills and detailed models added triangles; this has only been measured in software rendering, not on a real phone.
  • AI: traffic never changes lanes and keeps its speed on hills; city police can take detours when the grid route is blocked; police ignore traffic lights.
  • Physics: no real tyre grip or mass transfer; collisions use circles.
  • Structure: game.js is one closure of about 5,500 lines whose sections share variables.
  • Testing: the rules and the main browser workflows are tested; long sessions, every map end to end and sound quality are not. CI renders in software.
  • Persistence: best times live in one browser and can be edited by the player.

14 · Room 1

Plot Twist: Cell Block D

The first room of the game is a 3D escape room that rebuilds the course project Plot Twist as a prison break. The detective from the Ashford necklace case has been convicted of the theft and is now inmate 4471. Officer Hale locks them in washroom 2 for ten minutes. A hatch in the floor of the toilet stall is held shut by a four-digit lock; the code is hidden in the room. It lives in escape-room/, shares no files with the chase, and is played at /shard-heist/escape-room/.

Brief requirementIn the escape room
At least 5 scenesThe door, the sinks, the stall, the hatch, the tunnel
2 itemsSpoon (pries the crooked tile off the wall), mop (optional: jams the door)
2 endingsA: the hatch opens in time, down into the tunnel. B: time runs out, Hale takes you back to the cell
An ending that depends on an earlier decisionJamming the door with the mop buys one extra minute before Ending B, which can decide whether you reach Ending A

The puzzle

ClueWhere and howWhat it says
MirrorOnly visible after turning on the hot tap: the steam shows letters someone traced“UNSINKABLE?”
GraffitiScratched into the stall wall“She was unsinkable. She sailed only once. The year opens the floor.”
Scratches by the doorScratched into the wall beside the door“The ‘unsinkable’ went down on her first voyage. 15 April 19▒2.” (Behind the crooked tile, which only comes off with the spoon, is now a car key.)

Together they point to the Titanic and the code 1912; “sailed only once” gives the missing digit to players who do not know the history. The code is the same every time. Every wrong code makes noise and costs 30 seconds; Hale warns at 5:00, 2:00, 1:00 and 0:30. The plot twist comes in Ending A: a note on the ladder (“Took you long enough. A car is waiting. — H.”) shows the guard wanted the detective out, which leads into the chase.

How it is built

The structure is the one of the original Python project, rewritten in JavaScript: rules.js (213 lines) holds the story and the rules as pure functions, room.js (968 lines) only draws and turns clicks into actions.

// rules.js: one plain object is the whole state
state = { scene, time, inventory, clues, tileOpen, steam, wedged, graceUsed, lock, wrongTries, ending, warned }
perform(state, action, target)  →  { state, ok, message, cue }   // refused: the SAME state, nothing saved
tick(state, dt)                 →  { state, message, cue }       // the clock, warnings, grace minute, Ending B
visibleHotspots(state)          →  what can be used right now
restore(savedText)              →  a checked state, or null for anything that is not a real save

// room.js: a click becomes an action
marker or object clicked  →  use(action, target)  →  act()  →  rules.perform()
  accepted: keep the new state, save it, move the camera, syncWorld(), update HUD and markers
  refused:  show the message, play a short buzz, change nothing

Design decisions

  • Markers are real buttons. Each usable object gets a pulsing HTML button placed over it every frame, so the room works with a mouse, a keyboard and on touch screens, and the browser tests can click them. Clicking the 3D object itself does the same.
  • Viewpoints instead of free walking. Five fixed spots with free looking around keep the room readable and impossible to get stuck in.
  • The clock keeps running while reading clues and turning the lock; only the pause card stops it, and so does hiding the tab.
  • Saved after every accepted action, and checked field by field when loaded, like the SQLite save slot of the original but in the browser.

Limits and next steps

  • Not yet connected to room 2. Planned: the Ending A card gets a button that opens the chase.
  • Open decisions: 10 or 15 minutes (TIME_LIMIT), and whether the code should change between games (now always 1912).
  • Ending B and the grace minute are tested in the rules tests only, not in the browser test.
  • The Python original in plot-twist/ is a separate program with its own pytest tests and is not deployed.
